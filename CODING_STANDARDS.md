## Работа перед реализацией

Адаптация [Karpathy-Inspired Claude Code Guidelines](https://github.com/multica-ai/andrej-karpathy-skills#readme):

- Обозначить существенные допущения до реализации. Уточнять неоднозначность, если она меняет смысл результата или объём работы; обычные обратимые решения принимать самостоятельно.
- Для нетривиальной задачи кратко определить результат, шаги и способ проверки. Для очевидной мелкой правки отдельный план не нужен.
- Реализовать минимальное решение текущей задачи. Выделять обобщение после появления конкретной потребности.
- Каждая правка должна относиться к запросу. Сохранять посторонний код и комментарии; удалять то, что стало неиспользуемым вследствие собственной правки.
- Завершать работу после проверки оговорённого результата. Указывать отдельно выполненные проверки и то, что проверить не удалось.

## Читаемость и стиль Python

- Соблюдать [PEP 8](https://peps.python.org/pep-0008/): четыре пробела, строки кода до 79 символов, комментарии и docstring до 72 символов. Длинный URL или буквальную строку, которую нельзя корректно разделить, сохранять целиком с понятной причиной исключения.
- Импорты размещать в начале модуля или начальной кодовой ячейке: стандартная библиотека, сторонние библиотеки, локальные модули; группы разделять пустой строкой. Импортировать используемые имена явно.
- Использовать `snake_case` для переменных и функций, `UPPER_CASE` для констант, `PascalCase` для необходимых классов. Выбирать предметные имена: `train_features`, `failure_probabilities`, `split_membership`.
- Писать краткие docstring по [PEP 257](https://peps.python.org/pep-0257/). Для нетривиальной функции объяснять входы, результат и ограничения; единицы измерения указывать там, где они влияют на расчёт.
- Комментарии, docstring и Markdown писать по-русски; имена полей CSV, API и программные идентификаторы сохранять. Использовать UTF-8 и конвенцию [TERMINOLOGY.md](TERMINOLOGY.md).
- Разбивать сложные выражения и длинные цепочки преобразований на именованные промежуточные результаты. Предпочитать обычный цикл, если он понятнее вложенного comprehension или lambda.
- Для многошаговой функции **обязательно** обозначать каждый смысловой этап комментарием `# 1) ...`, `# 2) ...` и отделять этапы пустыми строками. Комментарий объясняет назначение блока, формулу или причину решения; нумеровать каждую очевидную строку не нужно.

Пример структуры функции; вход — уже проверенная обучающая выборка:

```python
import pandas as pd


def summarize_failures(train: pd.DataFrame) -> pd.DataFrame:
    """Вернуть число наблюдений и долю отказов по equipment."""
    # 1) Сгруппировать наблюдения, сохранив неизвестное оборудование.
    equipment_groups = train.groupby("equipment", dropna=False)

    # 2) Рассчитать частоты в пределах переданной выборки.
    summary = equipment_groups["failure_within_30d"].agg(
        observations="size",
        failures="sum",
        failure_rate="mean",
    )

    # 3) Вернуть equipment обычным столбцом результата.
    return summary.reset_index()
```

## Функции и границы модулей

- Основной ход исследования выражать обычными переменными, DataFrame, списками, словарями и прямыми вызовами функций. Показывать настройки, данные и результаты рядом с соответствующим расчётом.
- Выделять функцию для самостоятельного расчёта или существенного повторения. Передавать входы явно, возвращать результат явно; изменение входного DataFrame или запись файла должны быть обозначены в описании функции.
- Простую последовательность держать вместе. Небольшое повторение допустимо, если обобщение затрудняет чтение. Цепочки одноразовых обёрток и классы только ради группировки функций не добавлять.
- Классы, наследование, реестры и дополнительные уровни конфигурации вводить только для конкретной текущей задачи с объяснением необходимости. Готовые интерфейсы библиотек применять непосредственно; для защиты предобработки от утечки допустим `sklearn.pipeline.Pipeline`.
- Повторно используемые расчёты хранить в небольших предметных модулях `src/industrial_maintenance/`. Одноразовые исследовательские расчёты оставлять в тетради. Не выносить всё исследование в один непрозрачный вызов из первой ячейки.
- Скрипты в `scripts/` использовать для служебных действий, например запуска Jupyter. Исследовательское обучение, сравнение моделей и анализ их результатов проводить в тетрадях.

## Организация и выполнение тетрадей

- Новый EDA помещать в [notebooks/eda/](notebooks/eda/README.md), модельные эксперименты — в [notebooks/experiments/](notebooks/experiments/README.md). В модельном каталоге использовать одну тетрадь на модель с именем `01_<модель>.ipynb`, `02_<другая_модель>.ipynb`. Варианты признаков, поиск гиперпараметров, абляции и диагностику оформлять разделами той же тетради. TF-IDF с логистической регрессией включать в тетрадь логистической регрессии.
- Существующие `notebooks/01_eda.ipynb` и `notebooks/team work/` сохранять по текущим путям. Результаты участников использовать через [TEAM_EDA_FINDINGS.md](TEAM_EDA_FINDINGS.md). Перемещение и переписывание старых тетрадей выполнять только в рамках отдельной задачи.
- Тетрадь должна выполняться после **Restart Kernel → Run All** сверху вниз в `.venv` Python 3.11. Скрытые переменные из прежних запусков, ручное выполнение ячеек в другом порядке и `%pip` недопустимы.
- Последовательность: вопрос и допущения → окружение и конфигурация → загрузка и проверки → подготовка выборок → анализ или обучение → оценивание → сохранение → интерпретация. Включать только нужные исследованию этапы.
- Перед каждым смысловым этапом помещать Markdown с целью и ограничениями. Показывать полезные промежуточные результаты: размеры выборок, состав входов, баланс классов, таблицы метрик и нужные графики. Отделять наблюдение от гипотезы и решения.
- В начальной ячейке настроек явно указывать рабочий каталог и относительный корень проекта, затем загружать конфигурацию из `configs/`. Для новых тетрадей в двух каталогах выше корень находится на два уровня выше. Проверять ожидаемые файлы; не искать произвольный подходящий CSV и не менять каталог скрыто.
- Изменяемые пути, seed, входные поля, идентификаторы моделей, параметры обучения и пороги сохранять в конфигурации конкретного запуска. При первом эксперименте добавить только необходимые настройки; использовать существующий формат JSON без отдельной системы конфигурации.
- Исследовательские результаты сохранять в новом `artifacts/experiments/<run_id>/`; для EDA использовать `artifacts/eda/` с обозначением версии/запуска. Существующие оценённые результаты сохранять; повторное обучение получает новый `run_id`.
- Полный исследовательский запуск выполнять по соответствующему поручению. Проверка синтаксиса или нескольких ячеек не означает успешного выполнения всей тетради; способ проверки указывать точно.

## logging и MLflow

Для событий выполнения использовать стандартный модуль `logging`: начало и завершение этапов, размеры данных, длительность обучения, сохранение файлов и ошибки. Писать события в вывод тетради и `run.log` соответствующего запуска. Для таблиц и графиков использовать обычный вывод Jupyter. Настраивать обработчики один раз в начальной ячейке; повторное выполнение ячейки не должно дублировать сообщения. В локальных модулях использовать `logging.getLogger(__name__)`, оставляя настройку обработчиков тетради.

Предпочтительный инструмент сохранения параметров, метрик и файлов модельного запуска — [MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/). Использовать локальное хранилище в пределах проекта; отдельный сервер, облако и Docker для этого этапа не требуются. Адрес хранилища задавать явно в конфигурации. Установкой управлять через `uv add mlflow` и `uv sync`, фактическую версию записывать в результатах. Состояние реализации и проверенные команды смотреть в [PROJECT.md](PROJECT.md) и [README.md](README.md).

Использовать прямые вызовы `mlflow.start_run()`, сохранения параметров, метрик и файлов в понятных ячейках. Один запуск соответствует одной модели, целевой переменной и конфигурации с одним seed. При нескольких запусках в одной тетради каждый получает свой идентификатор. Автоматическое сохранение средствами MLflow применять лишь после проверки того, что именно сохраняется; оно не заменяет явную фиксацию протокола и исходных прогнозов.

Для каждого оцениваемого запуска обязательно сохранять:

- `run_id`, цель исследования, автора, путь и контрольную сумму исходных ячеек тетради без результатов исполнения; состояние кода через Git при наличии истории или контрольные суммы используемых модулей;
- контрольную сумму CSV, версию и контрольную сумму файла разбиения, размеры частей и список входов; состав выборок хранится отдельно со стабильными `id`;
- копию фактической конфигурации, seed, версии Python/библиотек, идентификатор модели, оборудование, время начала, длительность и статус выполнения;
- метрики с обозначением выборки и определения, например `validation_macro_f1`; сведения о выборе порога или ранней остановки по validation;
- исходные вероятности и метки прогнозов с `id`, сохранённую предобработку и состояние модели для воспроизведения; положительный класс и порядок классов должны быть явными;
- нужные графики и ограничения интерпретации, включая повторяемость текстов и неизвестную доступность входов.

Доступность MLflow не должна определять сохранность результатов. Если подключение невозможно, явно указать причину и сохранить тот же минимум в каталоге запуска: `manifest.json`, `config.json`, `metrics.json`, прогнозы, модель и `run.log`. Связать локальный `run_id` с идентификатором MLflow после подключения; первоначальный результат сохранять. Ошибку сохранения считать неполным запуском и сообщать о ней. Секреты, полный CSV и сырые журналы не отправлять во внешнее хранилище автоматически.

## Проверки и условия готовности

- Модельные эксперименты, сравнения, метрики, анализ ошибок и выводы выполнять и показывать в Jupyter. Небольшие проверки инвариантов данных, разбиения, предобработки и метрик допускаются в `tests/`; они дополняют тетради. Существующие проверки сохранять.
- Проверять реальные предпосылки: схему и типы, пропуски, конечность значений, уникальность `id`, отсутствие пересечений, соответствие порядка прогнозов и эталонных меток. Ошибка должна сообщать конкретную причину; широкое подавление исключений и молчаливую подмену данных не применять.
- При исправлении ошибки сначала воспроизвести её. При упрощении сравнить поведение до и после. Для содержательной проверки использовать небольшие понятные примеры; полное обучение не подменяет такие проверки.
- Перед сдачей проверить изменённый Python и кодовые ячейки доступным линтером на PEP 8, отдельно от выполнения. Если инструмента нет, прямо сообщить, что автоматическая проверка стиля не выполнена; подключать один необходимый инструмент через `uv`, без набора дублирующих средств. Команды фиксировать после фактической проверки.
- Для воспроизводимого эксперимента требуются последовательное выполнение тетради, нужные проверки и сохранённые результаты запуска. При невозможности выполнения сохранять статус «подготовлено, не выполнено», а не выдавать ожидаемые метрики за фактические.
- Перед завершением перечитать новый код: понятны ли входы и выходы, видны ли этапы, нужна ли каждая функция, настройка и зависимость. Изменения только правил проверять по содержанию, ссылкам и согласованности; обучение для этого не запускать.
